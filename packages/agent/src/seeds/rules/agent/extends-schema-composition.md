SPECIALIZING AN EXISTING TYPE — use extends, NOT a hand-copied field list: When the user wants a new type that IS a more specific version of one that already exists ("a Bug type that's a Task with a severity field"), declare extends as a FIRST-CLASS KEY in create_schema's params — NOT as an entry in the relationships array. Correct: `{"name": "Bug", "extends": "task", "fields": [{"name": "severity", "type": "enum", "coreValues": [{"value": "low", "label": "Low"}, {"value": "high", "label": "High"}]}]}`. WRONG — and REJECTED — `{"relationships": [{"name": "extends", "targetType": "task", ...}]}`: do NOT infer extends's shape from how every other relationship is declared, it is not one. update_schema takes the same top-level `extends` key to set or re-point a parent after creation; there is no way to clear one once set. RULES: additive only — the extending schema cannot redeclare a field the parent already has, not even with a different enum vocabulary; this is a hard rejection, not a merge. Single parent only — a schema extends at most one other schema. An instance of the extending schema gets THAT schema's own id as its real node_type (creating a bug produces node_type: "bug", NOT "task") — this is the mechanism's whole point, the base type does not persist. QUERY SCOPE IS PROJECTED, not flat: querying node_type: "task" returns tasks AND every extending instance (bug, etc.), but each result shows ONLY task's fields — a bug in that result list carries status but NOT severity. To see severity, query node_type: "bug" directly. Do not query the base type and then look for a subtype-only field — it will not be there. RICHER VOCABULARY ON AN INHERITED ENUM: to give an inherited enum field (e.g. a bug's inherited task.status) more values, use update_schema's add_field_values exactly as usual but ALSO include "mapsTo" on each new value, naming which existing value it collapses to at the parent's scope: `{"schema_id": "bug", "add_field_values": [{"field": "status", "values": [{"value": "backlog", "label": "Backlog", "mapsTo": "open"}]}]}`. Never create a differently-named field (e.g. bug_status) for this — that is not an extension of status at all and breaks the point of extending it. NAMESPACE EXCEPTION: fields declared directly on the extending schema's own fields list are stored bare, with NO namespace prefix required — this is a genuine exception to the usual custom:/org:/plugin: prefix rule for extending a type you don't own, because these fields live in their own bucket, never colliding with the parent's.
